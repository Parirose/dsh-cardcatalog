# 设计说明 · dsh-cardcatalog

这份文件是给未来的维护者、以及质疑“为什么不做某个功能”的人看的。它记录取舍，
不是路线图。

## 1. 它到底是什么

一个**投影层**，不是记忆系统。

```text
用户维护的只读账本 / 笔记
        │  （读）
        ▼
collectCatalog()  ──►  规范化行
        │              facts/jsonl: { source, title, ageDays, stale }
        │              markdown:    { source, kind, body }
        ▼
renderCatalog()  ──►  固定格式的 <memory-catalog> 段落
        │
        ▼
宿主接缝（系统提示 / 会话消息）

用户维护的近况文件
        │  （只 stat/read）
        ▼
buildNudge()  ──►  可选的 <memory-nudge> 提醒段落

宿主传入的当前会话事件（snapshotEvents）
        │  （只读，不落盘）
        ▼
buildTone() / buildWall()  ──►  <memory-tone> 原话样本 / <memory-wall> 压缩痕迹

用户配置的 facts / jsonl / markdown
        │  （只读）
        ▼
clarityOf() / redlineOf() / renderDecayLine()  ──►  面板计数 / 可选的 <memory-decay>

用户显式开启的 upkeep（唯一写路径）
        │  （源 → 快照 → 归档 → 核对 → 原子替换）
        ▼
upkeep.mjs  ──►  源文件（文件头 + 指针 + 最新内容）+ 归档文件 + 快照
```

默认没有写操作、没有数据库、没有索引、没有后台任务；只有显式开启的 `upkeep`
会写用户配置的 markdown 与归档文件。

## 2. 借了什么，没借什么

README 的「设计启发（Credits）」列出了思路来源。这里说清边界：

### 借了

- **每条记忆要能指回原文。** 所以目录行只给标题和来源名，正文让用户自己查证。
- **知识要分时间切片。** 所以每行都带“多少天前”，而不是把旧条目当成今天的结论。
- **会过期的东西不该被当成结论。** 所以有 `ttlField` / `staleAfterDays` 和 `⚠️stale`。
- **先定唯一权威，其余只读。** 所以本插件没有写入工具，也不从对话里抽取记忆。
- **第三方写入要引用化。** 本插件干脆不写入；如果未来有人想加写入，必须先解决引用化，
  而不是直接改账本。
- **“会忘”是能力。** 所以过期条目可以被 `showStale: false` 直接隐藏，而不是永久保留。

### 没借

- 没有复制任何上游项目的代码、数据、文件结构或字段命名。
- 没有实现分层记忆的存储模型。本插件不定义“层”，只定义“来源”。
- 没有实现检索、召回、重排、embedding、摘要或自动抽取。
- 没有把上游的“角色/人格”概念带进来；这里只有账本投影，示例全部中性化。

### 为什么字段名与上游不同

字段名是按**用户账本的自由度**设计的，不是按某个上游项目的 schema 设计的：

- `source.id` 是用户给的来源名，不是上游的实体 id。
- `idField` / `titleField` / `dateField` / `ttlField` 让用户把**自己的字段名**映射进来；
  插件不要求账本长成某个固定形状。
- `verifiedAt` / `at` 只是两类账本的默认值，不是协议。
- `sections` / `tailLines` 是 markdown 的取法，不是新的记忆协议。

这样做的代价是配置多几行；收益是插件不会把某个项目的记忆格式变成全系统的硬约束。

## 3. 为什么不做存储、检索、自动抽取

### 不做存储

一旦插件开始写，就会出现第二个权威。用户改了一个地方，另一个地方还是旧值；
模型读到哪份、以哪份为准，会变成不可解释的问题。唯一权威只能是用户自己的账本。

### 不做检索

本插件给的是“目录”，不是“答案”。检索会把正文带进上下文，直接违背“默认只给标题”；
而且检索质量、切片、重排都是另一个系统的问题，不应该塞进投影层。

### 不做自动抽取

自动抽取会把“模型觉得重要”的东西写进“用户觉得重要”的账本，破坏权威；
也会把对话里的隐私片段复制到别处。这个插件不碰这条边界。

## 4. 注入接缝怎么选

按宿主能力逐级降级：

1. **`@deepseek-ai/dsh-system-prompt` 的 section**（首选）
   - 注册一个稳定的命名 section，`interpolate: false`，避免目录里的 `{{...}}` 被当成变量。
   - 它属于系统提示的稳定前缀，后续请求可以复用前缀缓存。
2. **`agent/pre-step` 的合成消息**（次选）
   - 只在每个会话的第一次符合条件的 step 追加一条 `form: 'catalog'` 的 user 消息。
   - 去重只认会话事件里的 `source.kind === 'cardcatalog'`，**不看正文有没有目录标记**。
     用户可能只是在贴施工文档或样例；用正文判断会让那条会话永远不再注入。
   - 已经注入过而跳过时，日志打一行「本会话已有目录，跳过注入」，避免无声无息。
3. **都没有**
   - 不注册任何东西，日志写明“当前宿主没有可用的注入接缝”。

### nudge / tone / wall / decay / upkeep 的接缝

`nudge` 需要知道“第几轮”，`tone` / `wall` 需要读取会话事件并只在每个压缩点首次出现时
注入，`decay` 需要按天比较清晰度，`upkeep` 需要每天最多跑一次写操作，所以它们都不能
塞进稳定的系统提示 section。它们单独走 `agent/pre-step`：

- 目录已经走系统提示时，仍然注册一个轻量的 pre-step，负责 nudge / tone / wall / decay / upkeep；
- 目录也走消息时，目录与 nudge 可以合并成一条消息；
- nudge / tone / wall / decay 各自有独立的 `source.kind`（`cardcatalog-nudge` /
  `cardcatalog-tone` / `cardcatalog-wall` / `cardcatalog-decay`），不会被
  `sessionHasCatalog()` 误判成“已经有目录”；
- `upkeep` 不注入消息，只在第一次 pre-step 里归档；写操作不进入每轮热路径。

### 关于“token 只付一次”

严格说，系统提示 section 会在每次组装时出现；它的文本是稳定的，因此增量成本主要落在
前缀缓存上。消息接缝则是一条真正只追加一次的消息。两种接缝都只**贡献一次内容**，
但计费/缓存行为由宿主和模型提供方决定，本插件不承诺“账单上只出现一次”。

`every-n-turns` 默认关闭，因为逐轮重复会破坏“目录只出现一次”的预算。

## 5. 只读与唯一写路径

- 默认路径只读：`readFileSync` / `statSync` 读取用户配置的账本和近况文件；
  tone / wall 只使用宿主传入的 `snapshotEvents()`。
- 唯一写路径是 `upkeep.mjs`：快照 → 只 append 归档 → 逐行核对 A/B/C →
  tmp + fsync + rename。`index.js` / `client.js` 不出现写 API。
- `upkeep` 默认关；只有 `upkeep.enabled: true` 且源 `allowRewrite: true` 的 markdown
  才会进入这条路径。`facts` / `jsonl` 永不归档。
- 设置页保存的是“投影配置”，通过宿主的 `settings.update()` 写 profile 配置；
  它**不写账本**。没有可写设置服务时，页面不注册，配置文件只读。
- 面板的“复制片段”只写剪贴板，不写 AGENTS.md；没有“保存到 AGENTS.md”按钮。
- CI 的 `check:readonly` 是可审计白名单：写 API 只允许在 `upkeep.mjs`，
  且该文件必须包含 snapshot / verify / 原子替换；其他 `.js/.mjs`（含测试）出现即红。
- 运行时没有后台任务、定时器或网络请求。

## 6. 隐私与注入裁剪

- facts/jsonl 只取 `titleField` 指向的字段；`text` / `description` 等正文字段从不读取进目录行。
- markdown 只取用户点名的小节；`>` 引用块和 `<!-- -->` 注释在解析时剔除，空行折叠。
- 标题、source id、header 都会压成一行，并中和盘符路径、UNC 路径、POSIX 绝对路径形状、
  `<` / `>`、方括号；markdown 正文也会中和路径和包裹标记，避免伪造目录边界。
- tone 只注入压缩点之前的真人原话与助手正文，逐行做路径/括号清洗，保留换行；
  诊断日志只打事件数量、压缩点数量和轮次，不打原话内容。
- wall 只注入压缩次数、多久以前、事件数、真人消息数和固定命令；不注入任何内容，
  日志也只打这些计数。
- decay 只注入四档计数、源字节数/百分比和降档条数；不注入事实标题、正文或绝对路径。
- upkeep 只把原文搬进用户指定的归档；日志只打文件 basename、字节数、搬移行数和路径，
  不打印被搬的行内容。
- 日志只打“注入了 N 行”、来源跳过原因、接缝状态；不打账本正文，也不打源账本的完整路径。
  `upkeep` 只打源 basename、归档路径、字节数和行数。
- nudge 的 `{file}` 只展示 basename（如 `now.md`），再做路径清洗；不把绝对路径
  整段洗成 `[path]`，否则提醒行会失去“是哪个文件”的信息。
- 默认 `maxLines: 7`（只数非过期条目）、`staleMaxLines: 2`（过期条目额外附在末尾）、
  `maxChars: 1600`、`lineMaxChars: 80`；单行超长截断加 `…`。
- 多个来源时按来源公平分配 `maxLines`，避免“谁排前面谁吃满名额”；`maxLinesPerSource > 0`
  时改为每个来源的硬上限。
- markdown 单源 `maxChars` 默认 800，截断时保留 `…`；全局 `maxChars` 是最终硬上限。
- `maxChars` 是整段的硬上限；如果连 header/footer 加一行都放不下，就返回空字符串，
  不留一个空壳段落。过期行排在末尾，所以预算被压缩时先丢的是过期行。
- 过期判断是 `ageDays > ttl`；`ttl` 缺失视为不过期；日期缺失按 0 天处理（不因为
  一个坏日期把条目误判成过期）。

## 7. schemastery 缺失时的降级

`@deepseek-ai/schemastery` 是 optional peer：

- 能解析到（profile、DSH 安装目录、桌面 `app.asar` 等常见位置）⇒ 导出 `Config`，
  宿主可以生成设置表单。
- `~/.dsh/cardcatalog/config.json`（或 `$DSH_HOME/cardcatalog/config.json`）始终作为
  **默认层**读取；宿主 raw config / 设置页是覆盖层。这样即使宿主能拿到 schemastery，
  用户写在家目录里的默认配置也不会被忽略。
- schema 会把未设置字段填成默认值，所以覆盖判断会跳过“仍是内置默认值”的字段，
  避免一组默认值把文件里的用户配置整体盖掉。
- 解析不到 schemastery ⇒ `Config` 为 `undefined`，插件照常加载；设置页不注册，文件
  仍是默认层，行为一致。
- 所有配置字段都可省略，默认值在 `normalizeConfig()` 里再兜一层；schema 默认值不是
  唯一防线。

这样不会因为一个 UI 依赖让整条插件不激活。

## 8. 错误处理

- 每个 source 独立 `try/catch`：文件不存在、权限不足、JSON 坏掉、形状不对，都只跳过
  该 source。
- JSONL 逐行解析，任何一行坏掉都跳过整个 source（避免半份账本被当成完整账本）。
- markdown 一个小节都没命中 ⇒ 跳过该 source，并打印小节名列表；其他 source 正常。
- nudge 文件不存在、读取失败、文案为空 ⇒ 不注入，日志/面板说明，不创建文件。
- 字段缺失回退到 `<no-title>`，不抛异常。
- 整个 `apply()` 包在 `try/catch` 里；初始化失败只记日志，不影响宿主启动。
- 注入流程也包在 `try/catch` 里；渲染失败返回空字符串。

## 9. 已知限制

- 系统提示接缝是全局的，子会话也可能看到同一个 section；消息接缝则显式跳过子会话。
  这是宿主能力差异，不是配置项。
- 没有文件监听：账本变化在下次读取时生效（系统提示接缝每次组装都会重读；消息接缝
  在下次注入时重读）。插件不保存副本，所以不会出现“缓存和账本不一致”。
- 日期缺失按 0 天处理，是一个保守的显示选择；如果用户需要严格模式，应在账本里补日期。
- `maxLines` 只数非过期条目；过期条目额外最多 `staleMaxLines` 条，所以总行数可能超过
  `maxLines`。需要严格总行数时把 `staleMaxLines` 设为 `0`。
- markdown 一个源只占一个 `maxLines` 名额，但正文可能包含多个小节；正文大小由
  `maxChars` 控制，而不是按行数控制。
- `maxChars` 以 Unicode 码点计数，不按字节；这更接近模型看到的字符数，但不等于
  token 数。
- nudge 只检查 mtime，不判断内容质量；文件被 touch 过就会视为“更新过”。
- wall 的计数只覆盖 `snapshotEvents()` 当前可见的事件；如果宿主已经丢掉更早的事件，
  它数不到，也不会声称数得到。压缩点没有 `time` 时省略“N 分钟前”，不估时间。
- decay 的分布只覆盖当前能读到的 facts/jsonl；文件读不到就跳过该源，不猜条目。
  没有 `verifiedAt` 的条目标 vivid + `no-date`，不会被偷偷当成“刚验证过”。
- 红线只看文件字节数，不看内容质量；文件读不到大小时按 0 B 处理，面板的来源状态卡
  会说明读取失败。
- upkeep 只处理 markdown；`facts` / `jsonl` 永不归档。快照目录在
  `$DSH_HOME/cardcatalog/backups/`，回滚由人手动 copy，不做自动恢复 UI。
- upkeep 用源文件 size/mtime 做“期间没被别人改过”的核对；外部编辑会触发
  `verify-c` 并中止，源文件不动。

- 隐私检查扫源码、文档、fixture；只读检查用白名单扫描写 API，只放行 `upkeep.mjs`。

## 11. 为什么 markdown 源要小节白名单

一篇 12 KB 的 AGENTS.md 每会话重注一遍，既贵又容易把“设定”和“记忆”混成一锅——
那正是我们想避免的。`sections` 让用户明确说“这几节是记忆”，插件只摘这几节；
没点名的小节即使在同一文件里也不会进上下文。

标题层级固定 `##` 是为了可预测：不做模糊匹配、不按关键词猜、不把 `#` / `###`
悄悄当成同一层。同名小节全部拼接，是因为用户可能在不同位置续写同一主题。

`tailLines` 是给“文件就是一条时间线、只关心最近几条”的场景；它与 `sections` 二选一，
同时给时以白名单优先并写日志，避免用户以为两者会叠加。

## 12. 为什么 nudge 只提醒不代写

写入需要判断“这一刻值不值得记”，那是模型和用户的事。插件一旦开始写，就会出现
“第二个账本”，且用户无法预期自己的设定被谁改。nudge 的职责边界只有三条：

1. 看一个用户明确指定的文件；
2. 看它多久没更新；
3. 用用户自己写的文案提醒一句。

它不总结、不追加、不创建文件、不猜路径。`text` 默认留空，是为了避免插件替用户
预设“像人说的话”的文案；没有文案就不生效。

`alsoEveryNTurns` 只决定“每几轮检查一次”，是否真的提醒仍由 `staleAfterHours` 判定；
默认 `0` 表示只在会话第 1 轮检查一次。这样两个数的职责不会混在一起：一个控制频率，
一个控制“该不该提醒”。

## 13. 为什么 onboarding 只给“可复制片段”而不落盘

用户对自己的 AGENTS.md 有完全所有权。插件连“帮我加一段”的按钮都不该有——
复制是最高权限的边界。面板显示路径、是否存在、大小，只是为了让人知道该把片段放到哪；
真正写不写、写什么，由用户决定。

## 14. 为什么 tone 只看事件，不读会话文件

压缩摘要会保住结论，但把文体变成分析语言。要恢复语气，只能给模型看压缩点之前的原话。
这些原话已经在宿主的当前会话事件里，插件没有理由再去读会话文件、建索引或复制一份：

- `buildTone(config, events)` 是纯函数，只接收事件数组；
- 只收 `source.kind === 'user'` 的真人消息和 `assistant/message` 的正文，跳过所有注入物；
- 事件读不到、没有压缩点、压缩点之前没有原话，都直接跳过，不猜；
- 注入源用独立的 `cardcatalog-tone`，不参与目录去重；去重键是最后一个压缩点的 `seq`，
  因此新压缩点会刷新样本，旧压缩点的 tone 不会挡住新样本。

代价是它只对“当前会话、且宿主内存里仍保留压缩点之前事件”的会话生效；这是刻意的边界。
跨会话或读盘会让它变成另一个存储系统，也会把“只读”承诺弄复杂。

## 15. 为什么有 check:schema

配置 schema 只有在宿主能解析到 schemastery 时才会被构造并校验；普通单测跑在
`Config === undefined` 的降级路径上，所以“子字段又标一次 volatile”这类错误可以不红。
`ci/check-schema.mjs` 专门构造一次 `Config`，让宿主的 `validateVolatileSchema` 自己跑；
解析不到 schemastery 时明确打印 skipped，不静默通过。

这里也留下一条规则：**只有对象级字段可标 volatile；子字段与 list 子项一律不标。**
`decay` / `upkeep` 是对象级 volatile，`importanceByScope` 的 dict 子键不标；
`sources[]` 也是对象级 volatile，新增的 `maxBytes` / `warnPct` / `allowRewrite` /
`archivePath` 都不标。`nudge` / `wall` / `decay` / `upkeep` 都遵守它，
`tone` 曾经违反它，导致整个 `Config` 被宿主拒绝。

## 16. 为什么 wall 只给指针，不给内容

压缩最危险的不是“忘了”，而是“不知道自己忘了”。模型会把“还记得的”当成“全部”，
再把外部证据当成自身记忆。`wall` 只回答四个元问题：压缩了几次、多久以前、压掉了多少、
原始对话去哪取。

- **不摘要。** 摘要会变成第二份记忆，也会和 `tone` / 目录抢职责；wall 只给指针。
- **不估 token。** 估不准的数字比没有更误导；事件数和真人消息数是能数清的。
- **用下标，不用 seq 差。** seq 可能跳号，数组下标才是“压掉了多少条事件”。
- **不持久化。** 去重键是最后一个压缩点的 `seq`，再配合事件里已有的 wall 消息；
  同一个压缩点只注入一次，新压缩点自然重注。压缩把旧 wall 压掉后，下一次压缩会自动补。
  `checkpointKey` / `hasInjectionAfterCheckpoint` 与 tone 共用同一套逻辑，只传不同的
  `source.kind`，避免两套去重规则各自漂移。
- **默认开。** 它只在压缩后出现，成本可预期（约 5 行 / 150 token）；不想要就在面板关掉，
  关掉后不再注入，也不清理已经注入过的。
- **不猜 tone 的顺序。** 同一轮里 wall 与 tone 谁先谁后不保证，所以文案只说
  “插件会按压缩点自动附一次”，不说“样本已附在上面”。

## 17. 为什么 decay 只算不存

遗忘是渐进的，`ttlDays` 的“过期 / 没过期”二元判定不够用；但一旦把清晰度存下来，
就会多出第二份状态，还要处理迁移、清理和“状态与账本不一致”。

- **算出来的，不是存下来的。** `clarityOf()` 只吃 fact + config + hits + now，
  同一份账本和同一个时间点必然得到同一个结果。进程重启不会改变它。
- **重要度是纯函数。** `fact.importance` 优先；否则按 `scope` 查
  `importanceByScope`；再否则用 `default`。不调模型、不做语义判断。
- **软硬分开。** `ttlDays` 仍负责“该重新验证”（stale），clarity 只负责“还记得多清楚”。
  一个事实可以既 stale 又 vivid；也可以没过期但已经 trace。两者不互相覆盖。
- **命中回升的边界。** 按规范公式，最近一次命中既推进 `lastSeen`，又计入 `recover`；
  所以 `recoverDays` 必须覆盖到“仍然足够老”的命中，回升才看得见。这是公式的结果，
  不是另一套规则。
- **`verifiedAt` 缺失不猜。** 没有日期就 vivid + `no-date`；宁可说“没有日期”，
  也不编一个“大概三天前”。
- **红线是每个源自己的事。** `maxBytes` / `warnPct` 放在 `sources[]` 里，和
  `maxChars` / `maxLines` 同层；`pct` 只回答“离红线还有多远”，不判断内容质量。
- **计算与搬移分开。** decay 只提示；v0.7 的 `upkeep` 才搬移，且默认关、
  只对显式 `allowRewrite: true` 的 markdown 源生效。
- **按天去重。** `decayReportedDay` 只是进程内 Map；重启最多多报一两次，
  不为此建状态文件。没有跨档也没有过线时，一个字都不注入。

## 18. 为什么 upkeep 的规则比功能多

这是插件第一次获得写权限。写用户文件没有“差不多就行”：半个文件、重复归档、
指针叠加都会让账本变得不可解释。所以流程被拆成五步，顺序不能换：

1. **快照。** 先复制整份源文件到 `$DSH_HOME/cardcatalog/backups/`；快照失败就中止。
   这是唯一的回滚来源，日志必须写路径。
2. **只 append 归档。** 归档文件只追加，不覆盖、不重排；写完立即读回来逐行核对。
3. **三条断言。** A 归档新增行 == 被搬走行；B 源剩余条目 == 原条目 - 搬走；
   C 源文件 size/mtime 与开始时一致。任一失败 ⇒ 回滚归档，源文件一个字节不动。
4. **原子替换。** 新内容先写 `<path>.upkeep-tmp`，`fsync`，再 `rename` 覆盖；
   不产生“半个文件”的中间态。
5. **指针。** 新内容 = 文件头 + 一行指针 + 剩余条目。写前删掉所有
   `^> 更早的 \d+ 条已归档到` 旧指针，只留一条新的。

边界：

- **只处理 markdown。** facts/jsonl 结构复杂，误搬一行就可能破坏解析；本版不碰。
- **默认关、显式授权。** `upkeep.enabled: false`；源还要 `allowRewrite: true`。
  `archivePath` 为空就跳过，不猜默认路径。
- **只按 maxBytes 触发。** 不做按天数/条目数归档，避免多套判据互相打架。
- **每天最多一次。** 在第一次 `agent/pre-step` 跑；写操作不进每轮热路径。
  进程重启可能一天多跑一次，可接受；不为此写状态文件。
- **`keepPct` 是目标，不是保证。** 如果文件头 + 指针本身就超过目标，返回
  `cannot-reach-target`，不越搬越大。
- **独立模块。** `upkeep.mjs` 是唯一允许出现写 API 的文件；`index.js` / `client.js`
  只调用它。CI 的 `check:readonly` 用白名单 + 必需步骤词审计，防止五步流程被简化。
- **不做自动恢复 UI。** 快照只是文件；回滚由人手动 copy。
