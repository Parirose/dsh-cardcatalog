# 设计说明 · dsh-cardcatalog

这份文件是给未来的维护者、以及质疑“为什么不做某个功能”的人看的。它记录取舍，
不是路线图。

## 1. 它到底是什么

一个**投影层**，不是记忆系统。

```text
用户维护的只读账本
        │  （读）
        ▼
collectCatalog()  ──►  规范化行 { source, title, ageDays, stale }
        │
        ▼
renderCatalog()  ──►  固定格式的 <memory-catalog> 段落
        │
        ▼
宿主接缝（系统提示 / 会话消息）
```

整条链路没有写操作，没有数据库，没有索引，没有后台任务。

## 2. 借了什么，没借什么

README 的「设计启发（Credits）」列出了思路来源。这里说清边界：

### 借了

- **每条记忆要能指回原文。** 所以目录行只给标题和来源名，正文让用户自己查证。
- **知识要分时间切片。** 所以每行都带“多少天前”，而不是把旧条目当成今天的结论。
- **会过期的东西不该被当成结论。** 所以有 `ttlField` / `staleAfterDays` 和 `⚠️stale`。
- **先定唯一权威，其余只读。** 所以本插件没有写入工具，也不从对话里抽取记忆。
- **第三方写入要引用化。** 本插件干脆不写入；如果未来有人想加写入，必须先解决引用化，
  而不是直接改账本。
- **“会忘”是能力。** 所以过期条目可以被 `showStale: false` 直接隐藏，而不是永久保留。

### 没借

- 没有复制任何上游项目的代码、数据、文件结构或字段命名。
- 没有实现分层记忆的存储模型。本插件不定义“层”，只定义“来源”。
- 没有实现检索、召回、重排、embedding、摘要或自动抽取。
- 没有把上游的“角色/人格”概念带进来；这里只有账本投影。

### 为什么字段名与上游不同

字段名是按**用户账本的自由度**设计的，不是按某个上游项目的 schema 设计的：

- `source.id` 是用户给的来源名，不是上游的实体 id。
- `idField` / `titleField` / `dateField` / `ttlField` 让用户把**自己的字段名**映射进来；
  插件不要求账本长成某个固定形状。
- `verifiedAt` / `at` 只是两类账本的默认值，不是协议。

这样做的代价是配置多几行；收益是插件不会把某个项目的记忆格式变成全系统的硬约束。

## 3. 为什么不做存储、检索、自动抽取

### 不做存储

一旦插件开始写，就会出现第二个权威。用户改了一个地方，另一个地方还是旧值；
模型读到哪份、以哪份为准，会变成不可解释的问题。唯一权威只能是用户自己的账本。

### 不做检索

本插件给的是“目录”，不是“答案”。检索会把正文带进上下文，直接违背“只给标题”；
而且检索质量、切片、重排都是另一个系统的问题，不应该塞进投影层。

### 不做自动抽取

自动抽取会把“模型觉得重要”的东西写进“用户觉得重要”的账本，破坏权威；
也会把对话里的隐私片段复制到别处。这个插件不碰这条边界。

## 4. 注入接缝怎么选

按宿主能力逐级降级：

1. **`@deepseek-ai/dsh-system-prompt` 的 section**（首选）
   - 注册一个稳定的命名 section，`interpolate: false`，避免目录里的 `{{...}}` 被当成变量。
   - 它属于系统提示的稳定前缀，后续请求可以复用前缀缓存。
2. **`agent/pre-step` 的合成消息**（次选）
   - 只在每个会话的第一次符合条件的 step 追加一条 `form: 'catalog'` 的 user 消息。
   - 用会话事件里的 `source.kind` 和目录标记双重判断，避免重复注入。
3. **都没有**
   - 不注册任何东西，日志写明“当前宿主没有可用的注入接缝”。

### 关于“token 只付一次”

严格说，系统提示 section 会在每次组装时出现；它的文本是稳定的，因此增量成本主要落在
前缀缓存上。消息接缝则是一条真正只追加一次的消息。两种接缝都只**贡献一次内容**，
但计费/缓存行为由宿主和模型提供方决定，本插件不承诺“账单上只出现一次”。

这个取舍是刻意的：优先使用宿主推荐的系统提示接缝，同时保留消息接缝给没有该服务的宿主。
`every-n-turns` 默认关闭，因为逐轮重复会破坏“目录只出现一次”的预算。

## 5. 只读是怎么保证的

- 代码只使用 `readFileSync` 读取用户配置的账本；没有写入、追加、建目录、删除。
- 设置页保存的是“投影配置”，通过宿主的 `settings.update()` 写 profile 配置；
  它**不写账本**。没有可写设置服务时，页面不注册，配置文件只读。
- CI 的 `check:readonly` 对源码做一次 grep 断言；命中写 API 就红。
- 运行时没有任何后台任务、定时器或网络请求。

## 6. 隐私与注入裁剪

- 只取 `titleField` 指向的字段；`text` / `description` 等正文字段从不读取进目录行。
- 标题、source id、header 都会压成一行，并中和盘符路径、UNC 路径、POSIX 绝对路径形状、
  `<` / `>`、方括号；避免标题伪造目录边界或夹带路径。
- 日志只打“注入了 N 行”、来源跳过原因、接缝状态；不打账本内容，也不打账本路径。
- 默认 `maxLines: 7`、`maxChars: 800`、`lineMaxChars: 80`；单行超长截断加 `…`。
- `maxChars` 是整段的硬上限；如果连 header/footer 加一行都放不下，就返回空字符串，
  不留一个空壳段落。
- 过期判断是 `ageDays > ttl`；`ttl` 缺失视为不过期；日期缺失按 0 天处理（不因为
  一个坏日期把条目误判成过期）。

## 7. schemastery 缺失时的降级

`@deepseek-ai/schemastery` 是 optional peer：

- 能解析到（profile、DSH 安装目录、桌面 `app.asar` 等常见位置）⇒ 导出 `Config`，
  宿主可以生成设置表单。
- 解析不到 ⇒ `Config` 为 `undefined`，插件照常加载；设置页不注册，配置从
  `~/.dsh/cardcatalog/config.json`（或 `$DSH_HOME/cardcatalog/config.json`）读。
- 所有配置字段都可省略，默认值在 `normalizeConfig()` 里再兜一层；schema 默认值不是
  唯一防线。

这样不会因为一个 UI 依赖让整条插件不激活。

## 8. 错误处理

- 每个 source 独立 `try/catch`：文件不存在、权限不足、JSON 坏掉、形状不对，都只跳过
  该 source。
- JSONL 逐行解析，任何一行坏掉都跳过整个 source（避免半份账本被当成完整账本）。
- 字段缺失回退到 `<no-title>`，不抛异常。
- 整个 `apply()` 包在 `try/catch` 里；初始化失败只记日志，不影响宿主启动。
- 注入流程也包在 `try/catch` 里；渲染失败返回空字符串。

## 9. 已知限制

- 系统提示接缝是全局的，子会话也可能看到同一个 section；消息接缝则显式跳过子会话。
  这是宿主能力差异，不是配置项。
- 没有文件监听：账本变化在下次读取时生效（系统提示接缝每次组装都会重读；消息接缝
  在下次注入时重读）。插件不保存副本，所以不会出现“缓存和账本不一致”。
- 日期缺失按 0 天处理，是一个保守的显示选择；如果用户需要严格模式，应在账本里补日期。
- `maxChars` 以 Unicode 码点计数，不按字节；这更接近模型看到的字符数，但不等于
  token 数。

## 10. 测试策略

- `fixtures/` 是假账本：没有真实用户名、路径、标题、token。
- 纯函数测试（T1–T6）不依赖宿主：只验证“只给标题、会过期、缺文件不崩、没配置不注入”。
- 宿主接缝测试用假 context：验证系统提示优先、消息接缝只注入一次、子会话跳过、
  `every-n-turns` 间隔。
- 隐私检查扫源码、文档、fixture；只读检查扫源码里的写 API。
